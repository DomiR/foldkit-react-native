# Hermes performance of the native showcase

Measured on 2026-11-04 on the `hermes-perf-measure` branch.

## Summary

- The HBC artifact is 6.7 MB raw and 2.7 MB gzip. Minified JavaScript is 3.7 MB raw.
- Effect accounts for 1.4 MB, or 38% of minified JavaScript. Metro does not tree shake the Effect barrel, so modules such as `Graph`, `PersistedQueue`, `NetAddress`, the Schema arbitrary code, and the JSON Schema code ship even though the app does not use them.
- `foldkit` accounts for 1.8% of minified JavaScript. `@foldkit/native` accounts for 0.8%.
- Expo Go takes about 5 seconds from intent to the first Foldkit commit on both profiles. JavaScript entry to first commit takes about 4 seconds. Module evaluation takes about 2.7 seconds.
- From the modules evaluated mark to the first view takes about 0.1 seconds. The first view takes 8 ms. The first view to React commit takes about 0.5 seconds.
- Dispatch to committed frame takes about 50 ms at the median. One frame wait takes about 16.5 ms and React commit takes about 31 ms. Update takes 0.12 ms and view takes about 1.1 ms.
- Throughput is about 800 Messages per second for the largest bursts. Each burst produces exactly one view and one commit.

## Setup

The app uses Expo SDK 58, React Native 0.88, Hermes, Effect 4.1, and Expo Go 58. The measurement host is an Apple M3 Max.

The emulator is the `Foldkit_Perf_API_35` AVD. It uses Android 15, arm64, and the `sdk_gphone64_arm64` device model. Its configuration was copied from `Medium_Phone_API_35`. The two profiles are:

- `lowend`: 2 cores and 2048 MB of memory.
- `mid`: 4 cores and 4096 MB of memory.

Metro runs with `--no-dev --minify` and `EXPO_PUBLIC_FOLDKIT_PERF=1`. Each session includes the post boot settle step. Expo Go data is cleared once per session. Each session also has a build ID that is carried in every performance payload.

## Method

Bundle measurement uses two `expo export` runs. One produces the HBC artifact. The other produces minified JavaScript and its source map. HBC size is reported as a whole because bytecode is not source mapped per module. Minified JavaScript attribution uses the indexed source map, with one section per module. Generated byte ranges are assigned to source files and grouped by package.

Startup measurement force stops Expo Go for every run, clears logcat, and opens `exp://127.0.0.1:8082` with a VIEW intent. One warmup run is discarded. Ten runs contribute to each profile. The startup marks come from `performance.rnStartupTiming` and `performance.now()`. They are logged at the first React commit. Intent timing comes from the ActivityTaskManager START logcat line and the performance log line, both on the device clock. A build ID mismatch rejects a cached bundle.

The startup metrics use these endpoints:

| Metric                                | From                                                                  | To                                 |
| ------------------------------------- | --------------------------------------------------------------------- | ---------------------------------- |
| Load average before launch            | 1 minute load average from /proc/loadavg, read just before the launch | (a sample, not an interval)        |
| Intent to first commit                | ActivityTaskManager START line                                        | First Foldkit commit               |
| JavaScript entry to first commit      | React Native JavaScript bundle entry mark                             | First Foldkit commit               |
| JavaScript entry to bundle evaluation | React Native JavaScript bundle entry mark                             | Bundle evaluation mark             |
| Module evaluation                     | Bundle evaluation mark                                                | Modules evaluated mark             |
| Program creation                      | Modules evaluated mark                                                | `makeNativeProgram` returns        |
| Modules evaluated to first view       | Modules evaluated mark                                                | First view starts                  |
| First view                            | First view starts                                                     | First view ends                    |
| First view to commit                  | First view ends                                                       | First Foldkit commit               |
| Bundle evaluation to first commit     | Bundle evaluation mark                                                | First Foldkit commit               |
| Activity Manager launch time          | Activity Manager launch request                                       | Activity Manager launch completion |

The render benchmark uses the opt-in `NativeInstrumentation` hooks. `onUpdate` surrounds the application `update`. `onView` surrounds `view` before the native snapshot is published. `onCommit` runs in a layout effect after React commits the snapshot to the Fabric shadow tree and before the UI thread mounts it.

Each launch runs 200 latency samples. Two `requestAnimationFrame` callbacks and a phase-varying delay precede each dispatch. For each sample, the phases are:

| Phase      | Definition                       |
| ---------- | -------------------------------- |
| Queue      | Update start minus dispatch time |
| Update     | Update end minus update start    |
| Frame wait | View start minus update end      |
| View       | View end minus view start        |
| Commit     | Commit time minus view end       |
| Total      | Commit time minus dispatch time  |

Each burst synchronously dispatches N increment Messages for N equal to 100, 1000, and 10000. There are five repetitions per N. A burst ends at the first commit after a view that started after the Nth update. The report records the summed update time, view count, commit count, and counter count delta.

When instrumentation is omitted, the native runtime passes `update` and `view` through unchanged. `FoldkitRoot` adds no timing hook in that path.

## Interpretation

Frame pacing bounds the largest bursts. The Message queue processes Messages until it has spent `DRAIN_BUDGET_MS = 5` ms of synchronous work since the last yield, then hands the rest to a deferred drain scheduled with `setTimeout(0)`. React Native on Android fires that timer from the next frame callback, so a backlog drains in slices of about 5 ms per frame of about 16.7 ms.

At about 800 Messages per second, each slice holds about 13 Messages. That puts the runtime's work at about 0.37 ms per Message, of which `update` is about 0.05 ms. The rest of the 1.2 ms of wall time per Message, about 70%, is waiting for the next frame. The per Message cost in the runtime, about 7 times the cost of `update`, decides how many Messages fit in one slice.

During a burst, `renderFrame` waits while Messages are deferred. There is no intermediate frame render for the burst. The screen shows the counter jump once at the end.

Dispatch to commit is one frame wait plus React reconciliation and commit of the full showcase tree. The update and view phases are small fractions of that latency.

Startup is dominated by JavaScript module evaluation. Effect is the largest single package in the bundle. Module evaluation is where Effect's size appears in this measurement. The report does not measure evaluation time per module, so it does not assign an Effect share of evaluation time.

The two profiles land close together. Medians barely move between 2 cores with 2048 MB and 4 cores with 4096 MB on this host. The lowend profile widens the tails: startup P90 is 7,096 ms against 5,422 ms, and dispatch to commit P95 is 168 ms against 85 ms.

## Caveats

- Expo Go loads plain JavaScript from Metro and Hermes compiles it at launch. A release APK ships precompiled bytecode. These startup numbers are an upper bound for module evaluation and include Expo Go launch work and bundle download.
- Expo Go can launch a cached bundle. The build ID check rejects that bundle. There were 0 stale runs in both sessions. Startup depends on Expo Go's cache state, which the workflow resets once per session, so compare numbers measured with the same workflow.
- In Expo Go, `performance.rnStartupTiming` reports the same value for `startTime`, `initializeRuntimeStart`, and `executeJavaScriptBundleEntryPointStart`. The JavaScript entry mark therefore marks the start of the JavaScript runtime, and the time between the intent and that mark is Expo Go's own launch and bundle loading.
- The emulator runs on a much faster host CPU than a real low end phone.
- `onCommit` marks the React commit. It does not mark pixels on screen.
- One of three mid benchmark launches produced no logs within 180 seconds and was excluded. The report contains 2 launches and 10 samples per burst for mid.
- The 10,000 Message burst can stall. In one later mid launch it processed 5,672 updates in 62.8 seconds with no view and no commit before the harness timeout ended the launch, about 90 Messages per second instead of about 800. The cause was not isolated: emulator scheduling and runtime behavior under a large backlog both fit. Launches that hit the timeout are excluded from the tables.
- Latency maxima include emulator stalls. The lowend total latency maximum was about 5 seconds.

## Reproducing

Run these commands from the repository root:

```sh
examples/native-showcase/scripts/perf/emulator.sh create
examples/native-showcase/scripts/perf/measureDevice.sh lowend 10 3
examples/native-showcase/scripts/perf/measureDevice.sh mid 10 3
node examples/native-showcase/scripts/perf/bundleSize.ts
```

The workflow uses port 8082. Reports and logs land in `examples/native-showcase/.perf/`.
